# Эксплуатация oncomap-abai.kz (общая VPS)

На одной VPS работают Onco-GIS, портал заявок и портал обучения. Домашнюю
страницу Caddy отдаёт как статический файл; остальные пути направляются в
соответствующие контейнеры. Изменения лимитов находятся в
`deploy/onco-resilience.yml`, `deploy/requests-resilience.yml` и
`docker-compose.quality.yml`.

## Доступность

- Docker автоматически поднимает контейнеры после перезапуска VPS.
- Healthcheck проверяет Onco-GIS API, портал заявок и БД портала обучения.
- `quality-watchdog.timer` раз в минуту проверяет внешние маршруты и после
  трёх неудач перезапускает только отказавший контейнер.
- Caddy повторяет подключение к перезапускаемому backend до 5 секунд.
- Лимиты памяти: Onco-GIS 1300 МБ, заявки 512 МБ, обучение 1 ГБ, Caddy
  256 МБ. На VPS дополнительно настроен swap 2 ГБ как аварийный буфер.
- Gunicorn обучения: 2 процесса по 8 потоков, без ротации по числу запросов
  (`max_requests=0`). Ротация gthread под массовыми POST-запросами дала
  воспроизводимые обрывы соединений/502 на тестовой копии. Лимиты контейнера,
  перезапуск при отказе и контроль здоровья остаются включены.
- PostgreSQL-соединения повторно используются до 60 секунд, с проверкой
  здоровья перед повторным использованием. Это до 16 соединений у портала;
  `max_connections=80` оставляет запас для служебных операций. При увеличении
  числа процессов/потоков пересчитать этот бюджет.
- Проверять доступность: `/`, `/applications/`, `/quality/health/`.
  Healthcheck и watchdog не заменяют внешнее оповещение.

## Резервные копии

`quality-backup.timer` ежедневно запускает `scripts/backup-production.py`.
Копия включает согласованный `pg_dump` портала обучения (`quality.pgcustom`),
снимок SQLite портала заявок (`requests.sqlite3`), файлы Onco-GIS,
материалы обучения, код трёх сервисов и данные Caddy. Рабочий каталог
PostgreSQL в архив не добавляется. Контрольные суммы
записаны в `SHA256SUMS`. Локально на VPS хранятся 14 дней в
`/opt/quality-backups/daily-*`, доступ только root.

На VPS в `/opt/quality-backups/offsite` после каждого успешного резервного
копирования создаётся зашифрованный архив `.oncoenc` формата v2. Для этого
используется только открытый ключ `/opt/quality/offsite-public-v2.key`;
закрытый ключ на VPS не находится. Для проверки и восстановления нужны
**оба** локальных файла `offsite-private-v2.enc` и `recovery.key`:

```powershell
py -m pip install -r requirements-ops.txt
py scripts/offsite_public.py verify <имя.oncoenc> <путь-к-offsite-private-v2.enc> <путь-к-recovery.key>
py scripts/offsite_public.py restore <имя.oncoenc> <путь-к-offsite-private-v2.enc> <путь-к-recovery.key> <новый-пустой-каталог>
```

Старые архивы формата v1 восстанавливаются через `scripts/offsite_backup.py`.
В Google Drive отправляется **только** `.oncoenc`. Не загружайте туда
`recovery.key` или `offsite-private-v2.enc`, не отправляйте их в чат и не
добавляйте в Git. Храните вторую копию обоих файлов отдельно от компьютера.
Загрузка в Drive через подключение Codex сейчас выполняется вручную;
автоматическую отправку нельзя включать до настройки собственного Google
OAuth-клиента и проверки доступа rclone. Ежедневное создание зашифрованных
копий на VPS от Google Drive не зависит.

Перед восстановлением сначала расшифруйте архив в отдельный пустой каталог,
сверьте `SHA256SUMS`, проверьте `quality.pgcustom` через `pg_restore --list`,
а `requests.sqlite3` через `PRAGMA integrity_check`. Восстановите дамп
PostgreSQL сначала в отдельную тестовую БД и проверьте вход, число пользователей,
назначений и попыток. Никогда не распаковывайте архив прямо поверх работающего
`/opt` и не заменяйте действующую БД без проверенного отката.

## Пределы текущей архитектуры

Одна VPS остаётся общей точкой отказа; от проблемы у провайдера не спасёт
watchdog. Портал обучения переведён на PostgreSQL; портал заявок пока хранит
данные в SQLite. Это устраняет узкое место одновременной записи тестов в
SQLite. Проверка 320 активных HTTP-клиентов с просмотром курсов, началом
и отправкой тестов выполнена на изолированной копии общей VPS;
результаты и ограничения — в [отчёте](LOAD-TEST-2026-10-02.md).
Внешний сервис оповещения о недоступности ещё не подключён.

## Повторяемый нагрузочный тест

Рабочую базу не использовать для синтетических попыток. Скрипт
`scripts/load_staff_stand.sh YYYYMMDD_HHMMSS` создаёт уникальную БД
`quality_loadtest_*` из согласованного `pg_dump` и контейнер без публичного
порта. Нужны заранее скопированные `/opt/quality/scripts` и существующие
production `.env`, Docker-сеть и образ. Сидирование и проверка результата
отказываются работать с БД, имя которой не начинается с `quality_loadtest_`.

`load_staff_seed.py` меняет пароли **только в копии**, создаёт временные
назначения и закрытый `/tmp/load-manifest.json`. Его нельзя публиковать,
отправлять в чат или коммитить. Повторный этап запускается с аргументом
`full`; после каждого этапа новый манифест нужно скопировать из контейнера.

`load_staff_http.py` проверяет вход с CSRF, страницы сотрудника, начало теста,
отправку всех ответов, сохранение результата и запрет повторной сдачи после
успеха. Одновременные действия синхронизированы барьером, измеряется
фактический максимум HTTP-запросов. Входы ограничены отдельным параметром
`--login-concurrency` (1–32): 320 активных сеансов не равны 320 входам в одну
секунду. `load_staff_verify.py` отдельно сверяет записи попыток в копии.

Тестировать следует через частный Caddy (`scripts/load_staff.Caddyfile`),
как в production. Старые настройки ротации Gunicorn обрывали POST-запросы
даже через прокси; в текущей конфигурации ротация по счётчику отключена.
Генератор разрешает только имена тестовых контейнеров,
останавливается при доступной ОЗУ менее 400 МБ или двух последовательных
ошибках внешних проверок рабочего сайта. Лимиты генератора задавать отдельно
от приложения: его потоки и память не моделируют расход серверного Django.

По завершении сохранить обезличенные результаты, остановить только три
тестовых контейнера, удалить тестовую БД и манифест с временными паролями.
Проверить production healthcheck и сравнить число реальных попыток до/после.
Внешние Google Drive/YouTube и отрисовка в браузере этим HTTP-тестом не
проверяются. Нагрузочный тест снижает риск, но не гарантирует отсутствие
ошибок при любом трафике или отказе самой VPS.

Для обновления без сброса сеансов `scripts/rollout_quality.py` временно
переключает только quality-upstream Caddy на `quality_rollout`, затем
пересоздаёт основной контейнер и возвращает исходную маршрутизацию. До
запуска нужны резервная копия и проверенный образ. Для обновления без
изменения зависимостей можно собрать образ через `deploy/Dockerfile.runtime`
с `RUNTIME_IMAGE`, указывающим на сохранённый текущий образ.
Скрипту переключения передать `--artifacts /opt/quality-loadtest-<stamp>`:
это существующий закрытый каталог для резервной и временной копий Caddyfile.
